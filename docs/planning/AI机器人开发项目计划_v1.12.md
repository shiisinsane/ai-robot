# AI机器人开发项目计划 v1.12

> 文档定位：AI机器人项目的总体实施基线和三份规划文档的主入口。
> 当前范围：室内差速轮式移动机器人，不含机械臂。
> 技术基线：Ubuntu 22.04、ROS 2 Humble、VS Code + Codex；Claude可用于辅助审查。
> 总体顺序：先完成ROS 2机器人部分，再开发AI Agent部分。
> 详细规划：参见《ROS2机器人开发规划_v1.8》和《AI_Agent开发规划_v1.4》。

## 2. 项目目标

在Ubuntu服务器上建立一套可持续开发、测试、迁移和维护的AI机器人系统。项目先形成不依赖大模型也能独立运行的ROS 2机器人，再在其稳定能力接口之上开发AI Agent，最终实现：

```text
用户输入文字、语音、图片或视频
→ AI大模型理解任务并进行高层规划
→ AI—ROS 2接口生成受约束的物理任务
→ ROS 2完成感知、定位、导航和运动控制
→ 驱动、MCU和机器人本体执行动作
→ 系统返回任务进度、结果和异常
```

首个综合验收场景：

> 用户下达“去客厅门口看看有没有人”的任务，机器人能够解析地点、取得经过确认的目标位姿、自主导航、到点检测人员并反馈结果；遇到无效地点、定位失败、通信中断或急停时，能够拒绝任务或安全停车。

## 3. 总体原则

项目遵循以下原则：

1. **机器人先行**：ROS 2机器人必须先成为稳定、独立、可测试的执行系统。
2. **先模拟、后实体**：先在模拟环境验证对象、接口、子系统和整机能力，再进入实体开发。
3. **成熟资源优先**：优先复用ROS 2成熟开源资源，不无依据重写通用能力。
4. **统一接口**：仿真对象和实体对象采用相同的上层ROS 2接口。
5. **对象化与模块化**：要素职责单一、边界清晰、可独立测试、替换和扩展。
6. **分层测试**：单元、节点、契约、集成、系统、实体安全和AI端到端测试逐级推进。
7. **阶段门控制**：G1未通过不得进入实体机器人开发；G2未通过不得进入AI Agent开发。
8. **安全隔离**：AI Agent不能直接控制电机、持续发布速度命令或绕过机器人安全系统。
9. **增量改进**：除非明确决定重构，已通过验收的模块只做局部、可验证的增量修改。
10. **版本可追溯**：项目代码、配置、测试和规划文档统一纳入Git与GitHub管理，重要里程碑必须能够审查、复现和回退。

## 4. 系统分层与开发归属

| 归属 | 层级 | 主要职责 | 关键边界 |
|---|---|---|---|
| 系统入口 | 用户交互层 | 接收文字、语音、图片、视频并展示结果 | 不直接控制机器人 |
| AI Agent部分 | AI大模型层 | 多模态理解、任务理解和高层任务规划 | 不直接发布速度命令，不凭空决定物理坐标 |
| AI Agent部分 | AI—ROS 2接口层 | 结构化任务、语义目标物理化、合法性校验、能力调用和反馈 | 不替代Nav2、控制器和硬件安全 |
| ROS 2机器人部分 | ROS 2机器人软件层 | 感知、SLAM、定位、Nav2、机器人任务、运动和安全控制 | 不承担电机底层实时闭环 |
| ROS 2机器人部分 | 硬件驱动与本体层 | 底盘和传感器驱动、MCU通信、电机闭环及硬件安全 | 不理解自然语言 |
| 贯穿体系 | 研发与验证体系 | VS Code、Codex/Claude、Git、构建、仿真、测试和文档 | 不进入机器人运行时控制链 |

## 5. 两部分的依赖边界

ROS 2机器人部分先形成并冻结可独立调用的机器人能力，例如：

```text
获取机器人状态
导航到指定位姿
取消导航
检测人员
返回充电点
进入安全停车状态
```

AI Agent只能通过G2冻结后的Topic、Service、Action及自定义任务接口调用这些能力。ROS 2机器人在没有AI Agent时，也必须能够通过CLI、RViz2、测试程序或普通控制界面独立完成验收。

AI Agent只能调用白名单能力，例如：

```text
get_robot_status()
navigate_to(location)
detect_person()
cancel_task()
return_to_home()
```

禁止AI Agent：

- 直接控制电机或电机驱动器；
- 持续向`/cmd_vel`发布速度；
- 绕过任务管理、Nav2或安全节点；
- 自行执行任意Shell命令；
- 在未经确认的情况下把语义地点转换为物理坐标。

## 6. 总体实施顺序

```text
公共工程基线
    ↓
ROS 2模拟机器人开发
    ↓
G1：仿真到实体准入
    ↓
ROS 2实际机器人开发
    ↓
G2：ROS 2机器人能力验收
    ↓
AI Agent架构与任务协议
    ↓
AI大模型层和AI—ROS 2接口层
    ↓
AI仿真回归联调
    ↓
AI实体机器人联调
    ↓
整体稳定化与发布
```

在ROS 2机器人部分，自底向上是主要路线：

```text
设备/算法对象 → ROS 2节点 → 子系统 → ROS 2整机
```

在AI Agent部分，自顶向下是主要路线：

```text
用户任务 → 结构化任务 → 测试桩 → 仿真机器人 → 实体机器人
```

两条路线通过G2冻结的机器人能力接口汇合。

## 8. 阶段门

### 8.1 G1：仿真到实体准入

G1至少确认：

- 雷达、相机、IMU、底盘等独立仿真节点测试通过；
- 运动、感知、定位、导航和安全子系统集成测试通过；
- 仿真机器人能稳定建图、定位、导航、避障和安全停车；
- 正常、异常、取消、超时和故障注入场景通过；
- 仿真与实体统一接口冻结；
- 硬件候选、驱动兼容性、MCU通信和安全方案完成审查。

G1输出《仿真阶段测试报告》《实体接口冻结清单》《实体硬件与成熟资源选型表》和明确的准入结论。

### 8.2 G2：ROS 2机器人能力验收

G2至少确认：

- 实体机器人可脱离AI独立完成建图、定位、导航、避障、感知和安全停车；
- 仿真与实体公共能力接口一致；
- 每项能力都有成功、失败、取消、超时和状态反馈；
- 节点、契约、子系统、整机、实体安全和长稳测试通过；
- 能力接口、消息Schema、QoS、TF和错误码冻结；
- 仿真和实体回归测试环境可重复部署。

G2输出《ROS 2机器人能力清单》《ROS 2机器人综合验收报告》《AI调用接口冻结说明》《仿真与实体回归测试集》和明确的AI Agent准入结论。

## 10. 研发治理

- VS Code作为代码、配置、终端、调试和Git入口；
- Codex作为主工程代理，负责增量实现、测试、故障分析和文档维护；
- Claude可用于设计复核、代码审查和第二意见；
- ROS 2、Gazebo、测试程序、rosbag和实体日志提供客观验收证据；
- Git与GitHub保存阶段检查点、支持协作审查、问题跟踪、持续集成和版本回退；
- AI编程工具不属于机器人运行时，不在线直接控制实体机器人。

每个模块统一采用：

```text
明确职责和验收
→ 检索并评估成熟资源
→ 建立最小可运行样例
→ 冻结接口契约
→ 实现配置、适配或自研增量
→ 单元/节点测试
→ 子系统集成测试
→ 场景测试
→ 保存Git检查点和测试证据
```

### 10.1 GitHub项目仓库建立要求

M0阶段必须在GitHub创建AI机器人项目仓库，并将其作为本项目代码、配置、测试、规划文档和版本发布的统一远程基线。仓库暂定名称为`ai-robot`，实际创建时可根据GitHub命名情况确定；确定后应在三份规划文件和`README.md`中统一记录仓库地址。

仓库建立操作至少包括：

1. 在GitHub创建项目仓库；项目尚未确定开源范围时，默认先创建为私有仓库。
2. 在Ubuntu开发机创建或确认本地Git仓库，并把GitHub仓库配置为`origin`。
3. 使用`main`作为默认稳定分支，禁止把未经验证的试验直接作为稳定基线。
4. 首次基线提交至少包含：
   - `README.md`；
   - `AGENTS.md`；
   - `.gitignore`；
   - 许可证或《第三方许可证说明》；
   - 三份项目规划文件；
   - ROS 2工作空间源码、配置、脚本和测试目录；
   - 环境安装、自检、构建、测试和运行说明。
5. 完成首次推送，并在另一目录执行“克隆—安装依赖—构建—测试—运行最小节点”的复现检查。
6. 在仓库首页明确项目范围、Ubuntu/ROS 2版本、当前里程碑、构建入口、测试入口和安全警告。

### 10.2 分支、提交与审查要求

- `main`只保存已经达到当前里程碑验收标准的稳定内容。
- 日常开发使用短生命周期分支，例如`feature/*`、`fix/*`、`docs/*`和`test/*`。
- 每次提交只完成一个边界清晰的变更，提交说明应能指出模块、目的和影响。
- 代码、接口、构建配置、安全逻辑和阶段门材料的变更，应通过Pull Request审查后合并。
- Pull Request必须说明变更内容、测试结果、风险、回退方法，以及是否影响ROS 2接口、TF、QoS、硬件安全或AI调用边界。
- 不得使用强制推送覆盖`main`的公共历史；发现问题时使用可审查的修复提交或回退提交。
- AI工具生成的代码不能未经构建、测试和人工确认直接合并到`main`。

### 10.3 Issue、里程碑与项目跟踪要求

- 在GitHub中建立M0～M17和G1、G2对应的Milestone，或建立等价的项目看板字段。
- 开发任务、缺陷、技术债务、资源选型和测试异常统一建立Issue，不以聊天记录代替正式任务记录。
- Issue至少标明所属规划、模块、里程碑、优先级、验收标准和负责人。
- 建议使用`ros2`、`simulation`、`hardware`、`ai-agent`、`bug`、`test`、`safety`、`documentation`等标签分类。
- G1和G2关闭前，相关阻塞Issue必须关闭，或形成经确认的延期与风险处置结论。

### 10.4 版本、发布与回退要求

- M0、M1及G1、G2等重要检查点完成后创建Git标签，标签与项目版本规则保持一致。
- 稳定交付通过GitHub Release发布，附变更说明、兼容环境、测试结论、已知问题和回退说明。
- 规划文档版本号、Git提交、标签、软件包版本和测试报告之间应能够相互追踪。
- 任何影响冻结接口的修改都必须提升相应版本、更新变更记录并重新执行契约与回归测试。

### 10.5 自动化、安全与大文件要求

- 建立GitHub Actions或等价持续集成流程，至少执行格式检查、构建和自动测试；实体运动测试不得在无人值守的云端流程中触发。
- 密码、令牌、API Key、GitHub凭据、Wi-Fi信息、私有模型地址和设备密钥不得提交到仓库；使用环境变量和本地忽略配置。
- 提交前启用密钥泄露检查；如发生误提交，应立即撤销凭据并清理风险，不能只删除最新文件。
- rosbag、模型权重、地图原始数据、构建产物、日志和大型二进制文件默认不直接进入普通Git历史。
- 确需版本化的大文件使用Git LFS、发布附件或受控外部存储，并在仓库中保留来源、校验值、版本和获取说明。
- `build/`、`install/`、`log/`、临时数据、IDE缓存和本地密钥文件必须写入`.gitignore`。
- 仓库权限遵循最小授权原则；私有仓库转为公开仓库前，必须完成许可证、凭据、个人信息、硬件资料和第三方代码审查。

## 11. 版本与变更规则

1. 主文件和两份子规划分别维护版本号。
2. 每次修改文档正文，都必须提升该文档的版本号，同时修改文件名和文档内部版本标识；不得用更新后的内容覆盖原版本文件。
3. 未发生内容变化的其他规划文件保持原版本号，不因关联文件升级而被动升级。
4. 项目级范围、开发顺序、阶段门或分层边界变化时，更新主文件。
5. ROS 2对象、资源选型、仿真、硬件和机器人测试变化时，更新ROS 2规划。
6. 模型、任务协议、AI接口、语义映射和AI联调变化时，更新AI Agent规划。
7. 涉及G2接口的修改必须同步检查两份子规划，并重新执行接口契约和回归测试。
8. 除非明确要求重构，所有“优化、完善、补充、升级”均按现有基线做增量修改。

## 13. 项目完成判定

只有同时满足以下条件，项目才算完成：

- ROS 2模拟阶段、实体阶段和AI Agent阶段均通过综合验收；
- G1和G2阶段门均有正式结论和测试证据；
- ROS 2机器人脱离AI后仍可独立运行；
- 仿真与实体使用相同的上层机器人能力接口；
- 每个关键对象可独立启动、测试、替换和诊断；
- 成熟资源的来源、版本、许可证、配置和测试均可追踪；
- 单元、节点、契约、集成、系统、实体安全和AI端到端测试形成自动回归；
- 硬件急停、通信失联停车和速度限制有效；
- AI Agent只能通过受约束的白名单能力调用ROS 2；
- 综合场景能够重复完成，而不是偶然演示成功；
- 环境、代码、配置、测试和操作文档可以复现；
- GitHub仓库中的Issue、提交、Pull Request、标签、发布版本和测试证据能够相互追踪；
- 能够从指定GitHub发布版本重新克隆、构建、测试并恢复可运行基线；
- 发布版本可诊断、可维护、可扩展并可回退。
