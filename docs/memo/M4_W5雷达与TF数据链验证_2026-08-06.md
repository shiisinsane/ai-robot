# M4-W5雷达与TF数据链验证记录

> 日期：2026年8月6日
> 结论：通过，允许进入M4-W6相机基础处理链

## 1. 实现范围

- 新增`check_m4_lidar_tf.py`，验证运动雷达、完整TF链、障碍物空间语义及断流；
- 在统一Bringup中新增`enable_lidar_pipeline`故障注入参数，默认保持`true`；
- 正常模式保持`/robot/scan`公共接口、LaserScan类型、Best Effort QoS和`laser_link` Frame；
- 故障注入仅关闭公共雷达适配链，不改变Gazebo传感器、EKF、底盘或其他传感器状态；
- 未提前实现W7安全监督器，W5只验证断流可复现和可观察，不宣称已触发安全停车。

## 2. 整机自遮挡问题与修正

首次整机运行时，雷达正前方持续检测到约`0.148 m`回波，而不是距离约`1.8 m`的红色障碍物。
检查确认M3独立雷达模型没有相机，因而未暴露该问题；整机组合后，相机外壳顶部与原雷达
`z=0.10 m`扫描平面相交，形成真实自遮挡。

处置如下：

- 将`laser_link`相对`base_link`的Z高度从`0.10 m`提高到`0.14 m`；
- 相机顶部为`0.105 m`，修正后扫描平面保留`0.035 m`垂直间隙；
- 将当前传感器配置由`m3.v1/simulation_initial`提升为
  `m3.v2/simulation_integrated`；
- 在`check_sensor_model.py`中加入“雷达扫描面必须高于相机外壳至少0.01 m”的确定性检查；
- M3归档中的`m3.v1`仍保持原验收快照，不覆盖历史结论。

## 3. 正常运行验证

在隔离的`ROS_DOMAIN_ID=168`和独立Gazebo分区中执行静止、低速后退和原地左转：

| 场景 | 雷达观测 | 变换到`odom`后的障碍物坐标 |
|---|---|---|
| 初始静止 | `1.800 m`，`0.009 rad` | `(1.800, 0.016) m` |
| 后退1秒 | `1.992 m` | `(1.791, 0.052) m` |
| 左转1秒 | `-0.551 rad`，障碍物位于雷达右侧 | `(1.791, -0.018) m` |

验证结论：

- 雷达仿真时间频率为`15.152 Hz`，高于10 Hz门限；
- 时间戳严格递增，Frame为`laser_link`，每帧360点；
- 后退后障碍物相对距离正确增加；
- 左转后障碍物相对方位正确转到机器人右侧；
- 机器人运动前后，同一障碍物在`odom`坐标中的位置保持在容差内稳定；
- `odom → base_link → laser_link`完整TF链持续可用。

## 4. 断流故障注入

使用`enable_lidar_pipeline:=false`启动隔离场景，并运行
`check_m4_lidar_tf.py --expect-timeout`：

- 5秒窗口内`/robot/scan`消息数为0，确认公共雷达链断流；
- 同一窗口内`/robot/odom`收到205条，确认EKF与底盘未被故障注入误停；
- 断流能够稳定复现并由Topic新鲜度观察；
- 本阶段不执行故障锁存、诊断码或安全停车，这些属于W7。

## 6. 已知边界

- 当前只验证已知静态障碍物，没有实现代价地图、聚类、目标识别或避障决策；
- W5断流注入只证明数据链缺失可观察，不代替W7的安全监督与停车验证；
- 雷达安装高度已形成`m3.v2`当前配置，后续模型调整必须继续检查相机、雷达和外壳遮挡关系；
- 本阶段未改变公共Topic、消息类型、QoS或Frame名称。
