## 2. 候选矩阵

- 5条路线；
- none、low、medium三档障碍；
- none、low、medium三档定位条件；
- 共45个场景单元；
- 候选为8个完整随机区组，共360项任务；
- 以完整区组划分：训练4组、验证2组、封存测试2组。

候选计划由固定种子`20260828`确定性生成。路线修复后的当前候选SHA-256为
`3a2f2d79ab28949260f49572d061c61a5f93392a5f859a68af92fec1972ab643`；旧哈希
`2b8f97a4409b6a9dd178ea7997927d19cb27ad00e6bb1229797809c114603450`已被本次静态设计修复替代。
采集顺序固定为训练
1～180、验证181～270、封存测试271～360；只随机化每个区组内部45个场景。这样后续任务的

360项是当前用于评审的固定设计候选，不是已授权执行数量。正式预注册前仍需评估运行成本、

## 3. 任务前数据快照

任务接受前需要记录路线与目标几何、障碍和定位配置、AMCL协方差及位姿年龄、scan/odom/安全
状态年龄、必需Topic完整性、Nav2节点Active状态、安全停车状态，以及严格滞后的最近10项历史
计数。字段草案见`config/w7_preacceptance_snapshot_v0.1.yaml`。

任务终态、错误码、周期、任务执行后反馈和全程遥测均禁止进入任务前模型。缺少必需快照的尝试
应在派发前判为无效，不允许在任务结束后补填特征。

## 4. 尚未关闭的门禁

静态源码探测表明，现有Runner已经在派发前等待`odom`、`pose`、`scan`、`safety`和`diagnostics`，
并确认仿真时钟推进、任务Action可用和安全停车解除；`pose`消息本身也包含所需协方差。但是当前
Runner只保存“是否见过Topic”，没有在`send_goal_async`之前固化各消息时间、协方差和内容，
Collector则主要在任务激活后生成整秒桶。因此这些信息在接口上可获得，却尚未形成无泄漏的
`preacceptance_snapshot`记录。

任务前快照已于2026-08-28接入求职支线Runner：它读取最新定位协方差和各消息时间，查询四个
Nav2生命周期节点，并在`requested`和`send_goal_async`之前发布`preacceptance_snapshot`。过期、
缺失、安全停车激活或Nav2未全部Active时失败关闭。旧版复现默认不启用；B2必须显式传入
`--preacceptance-snapshot-required`。严格滞后的最近10项历史计数由批次编排器显式传入，不能靠
单任务进程内存推测。

离线测试已覆盖快照构造、过期拒绝、结果字段排除及事件顺序。快照同时保留在原始
`task_context`JSON并加工为独立`fact_task_preacceptance`事实表。B2额外执行每任务唯一性、原始/
事实对账、请求前时序以及配置与Ready状态四项门禁；旧版数据库即使没有该新增表也可继续只读
审计。尚未在真实ROS图中验证生命周期服务名、消息新鲜度和Collector落盘。

1. 确认5条路线在静态地图和全局代价地图中起终点均可用；
2. 验证none/low/medium障碍实际模型位置与全局规划可达性；
3. 在隔离ROS域中验证任务前快照可稳定获取并落盘；
4. 每条路线×每档障碍至少完成一次GUI资格Pilot并由用户人工确认；
5. 冻结正式样本量、随机计划、重试规则和测试集清单；
6. 获得用户对正式采集的单独明确授权。

因此当前只判定“静态设计可进入接口探测和资格准备”，不判定B2已预注册或可正式采集。

## 5. 严格滞后历史实现

`pipelines/b2_v0_3/lagged_history.py`只接受当前`plan_index`之前且已通过样本门禁的连续有效结果，
取最近10项计算任务数、失败数和超时数。缺少任何前序有效槽位时失败关闭；计划首项明确记录
`no_history=true`。通用批次Runner对B2计划强制要求任务前快照和显式历史参数，不再用默认0代替
缺失历史。

训练、验证、测试按时间依次采集，使验证历史只依赖训练及更早验证任务，测试历史可以依赖实际
已发生的开发阶段任务，但训练特征绝不会依赖验证或测试结果。
