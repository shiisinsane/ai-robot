## 1. 建设目标

本附加任务面向数据科学岗位求职，在不改变已通过 G1 验收的机器人项目基线的前提下，
复用现有 ROS 2 仿真、导航、任务管理、安全监督、故障注入和测试证据能力，完成一套可复现的
“业务问题—指标口径—数据获取—数据治理—分析诊断—风险建模—策略实验”闭环。

最终目标不是证明已经获得真实商业收益，而是形成一个证据充分、边界诚实、能够独立讲解的
仿真运营分析案例，并产出可以写入简历的真实数据量、模型指标和策略实验结果。

计划支撑的简历表述如下；其中所有占位数字必须由实际实验产生，未完成相应验收前不得写入简历：

1. 围绕每机器人单位时间有效任务数建立指标体系，将任务完成率、任务周期和恢复/介入率作为
   核心指标，并设置最小障碍距离、安全停车率等护栏指标。
2. 设计任务、事件、遥测及设备/实验维度数据模型，基于 ROS 2 运行日志构建 ETL 流程，处理
   重复任务、时间戳错位、缺失终态和测试数据污染等质量问题。
3. 使用 SQL 按区域、路线、任务阶段和参数版本拆解失败与耗时，定位主要异常场景，并通过
   可复现仿真实验验证原因。
4. 基于 `N` 次仿真任务构建任务失败风险模型，对比规则基线、逻辑回归与树模型，在独立测试集
   上取得 `PR-AUC=X`、失败任务召回率 `Y`。
5. 将分析结论转化为任务前定位检查、风险任务重定位和模拟人工介入策略；在 `N` 次受控对照
   实验中，使超时率由 `A` 降至 `B`、单位时间有效任务数变化 `C%`，且安全护栏无明显恶化。

大型 rosbag、原始图像、完整遥测、模型二进制和临时输出继续遵守正式项目的数据规范，不进入
普通 Git 历史。其来源、版本、大小、SHA-256 和复现方法可以写入附加任务证据索引。

### 2.2 基线保护

- 默认只读取和调用已验收的 M4～M6 公共接口，不修改其契约、验收门限和归档结论。
- 不修改 `docs/backs/milestones/` 中的已归档证据。
- 不把本附加任务的实验结果写成 M4～M6 或 G1 的补充验收结果。
- 不因本任务启动 M7，不选型、连接、上电、写入或操作实体设备。
- 不因本任务启动 M12～M17，不正式开发或接入 AI Agent。
- 如确需修改 `src/`、`config/common/` 或既有正式回归脚本，应先证明只读适配无法满足需求，
  单独评估对已验收基线的影响，并获得用户明确授权。
- 优先在附加目录中实现采集适配器和实验编排，通过现有 Topic、Service、Action 读取数据。
- 所有 ROS 2/Gazebo 实验必须设置独立 `ROS_DOMAIN_ID`；并行 Gazebo 还需使用独立 Transport
  分区，严格遵守根目录 `AGENTS.md` 的运行隔离要求。

### 2.3 结论边界

- 对外名称必须包含“仿真”或明确说明数据来自受控仿真实验。
- 不虚构真实客户、生产部署、收入、成本节省、人工团队或实体机器人运行结果。
- “人工介入率”仅在真实记录操作事件后使用；第一版优先采用“恢复/介入率”。
- 故障注入样本与自然运行样本必须分别标记，不能把故障注入分布解释为真实运营分布。
- `5/5` 只代表既有 M6 小规模综合验收，不得表述为普遍的“100% 成功率”。

### W1：定义业务问题、指标树和口径字典

状态：已于 2026-08-19 完成。交付物为 `reports/metric_tree.md`、
`schemas/metric_dictionary.yaml`、`reports/metric_definition_review.md` 和
`tests/test_metric_dictionary.py`。W2 已冻结指标所需的数据模型，可执行指标 SQL 将在 W6
实现，因此简历条目 R1 仍未准入。

目标：把“机器人技术指标”转化为可用于运营决策的业务指标。

业务问题：在满足安全护栏的前提下，如何提高单位仿真运行时间内的有效巡检任务完成数？

至少定义：

- 北极星指标：每机器人单位仿真时间有效完成任务数；
- 核心指标：任务完成率、准时完成率、任务周期、恢复/介入率、路径效率；
- 护栏指标：最小障碍距离、安全停车率、超速次数、传感器过期率；
- 诊断指标：定位、规划、控制、感知和安全阶段的失败率及耗时；
- 数据过滤：测试请求、重复提交、用户取消、故障注入和无效实验的处理方式；
- 业务 SLA：由基线实验确定候选值，再冻结正式阈值，不得凭空填写。

交付物：指标树、指标字典、事件定义、业务口径评审记录。

验收：每个指标均具备名称、业务含义、公式、分子、分母、粒度、时间窗口、过滤规则、数据源
和限制说明；不同人按字典计算应得到相同结果。

### W2：设计分析数据模型

状态：已于 2026-08-19 完成。交付物为 `schemas/warehouse.sql`、
`schemas/data_dictionary.yaml`、`schemas/seed_dimensions.sql`、`reports/data_model.md`、
`reports/data_lineage.md` 和 `tests/test_warehouse_schema.py`。由于当前环境未安装 DuckDB，DDL 采用
DuckDB/SQLite 兼容语法并已通过 SQLite 内存库验证；DuckDB 引擎验证留待 W5 环境建立时关闭。

目标：建立能够支持 SQL 分析、模型训练和实验追溯的数据层。

至少设计：

- `fact_task`：一行表示一次任务执行；
- `fact_task_event`：一行表示一次任务状态或关键事件变化；
- `fact_task_telemetry_1s`：一行表示某任务一秒钟的遥测聚合；
- `dim_scenario`：地图、区域、路线、障碍和噪声场景；
- `dim_experiment`：批次、代码、配置、参数、ROS 域和故障注入信息；
- `dim_error_code`：错误码、失败阶段和责任分类。

本地分析引擎默认使用 DuckDB，交换格式优先使用 Parquet；选择其他方案时需记录理由。

交付物：数据库 DDL、ER/关系说明、字段字典、主外键和粒度说明。

验收：任务表能与事件、遥测、场景和实验稳定关联；明确处理一对多 Join，避免指标重复计算；
所有模型特征可追溯到原始字段和生成逻辑。

### W3：建立结构化采集和实验编排

目标：将现有 ROS 2 任务与遥测输出转换为稳定、机器可读的实验记录。

任务：

1. 在附加目录实现只读采集节点，订阅任务反馈、TF、里程计、雷达、安全状态和导航状态。
2. 在附加目录实现实验编排器，通过已冻结的公共任务 Action 发起任务，不直接发布速度命令。
3. 每次任务记录实验 ID、任务 ID、起止时间、目标、阶段、终态、错误码、耗时、位置/航向误差、
   场景、参数版本和 Git 提交号。
4. 继续使用现有 rosbag 规范保存可回放的原始证据。
5. 为采集器建立小型确定性测试和缺失 Topic/时间跳变测试。

交付物：采集器、实验编排器、结构化 JSONL/Parquet 样例、采集测试。

验收：同一任务的结构化记录与 Action 结果、日志和 rosbag 一致；采集组件只读观察公共能力，
不改变机器人控制和安全链。

### W4：设计并执行仿真实验矩阵

目标：获得覆盖正常、困难和异常场景的可分析数据集。

第一版建议目标：

- 总任务数不少于 300；
- 至少 3 类路线和 3 档障碍难度；
- 至少 3 档初始位姿/航向扰动；
- 至少 2 套参数版本；
- 覆盖定位、规划、控制、感知超时和安全停车场景；
- 每个主要失败类别尽量不少于 20～30 条；
- 正常自然运行与人工故障注入使用独立字段标记。

样本数不是固定的统计充分性证明。正式停止采集前，应根据失败比例、置信区间、分组覆盖和训练
评估稳定性决定是否增加样本。

交付物：实验矩阵、运行清单、原始证据索引、数据集版本清单和样本分布报告。

验收：实验可按配置重复执行；每条记录可追溯到代码、参数、场景和原始证据；数据覆盖支持
后续分组分析和模型评估。

### W5：构建 ETL 与数据质量体系

目标：把任务、事件、遥测和实验配置加工为可信的分析表与模型特征表。

ETL 至少包括：

1. 解析任务结果和事件流；
2. 统一仿真时间和采集时间；
3. 按任务时间窗口关联遥测；
4. 生成一秒级聚合和任务级特征；
5. 写入 DuckDB/Parquet；
6. 输出数据版本和质量报告。

质量检查至少覆盖：

- 重复任务 ID；
- 缺失或冲突终态；
- 结束早于开始；
- 非法状态迁移；
- 同一机器人非法任务重叠；
- 时间戳倒退、跳变或跨时钟混用；
- 遥测窗口覆盖不足；
- 成功结果携带非零错误码；
- 失败结果缺少错误分类；
- 测试或故障注入数据污染业务口径；
- 一对多 Join 导致任务数膨胀。

交付物：ETL、数据校验器、脏数据夹具、质量测试、质量报告和分析数据库。

验收：故意构造的重复、缺失、错时、非法终态和污染样本均能被识别；相同输入重复运行得到
一致输出；核心任务数可从原始证据对账。

### W6：使用 SQL 完成业务分析和原因验证

目标：用 SQL 回答运营问题，并将相关性结论推进到可复现实验验证。

至少回答：

1. 单位仿真时间有效完成任务数由哪些环节决定？
2. 失败和长耗时主要集中在哪些阶段、路线、场景和参数版本？
3. 哪些任务贡献了大部分超时、恢复或安全停车？
4. 哪些任务在开始前或早期应执行重定位或进入模拟人工检查？

SQL 至少覆盖：

- 整体和分组 KPI；
- 任务阶段漏斗；
- 失败原因 Pareto；
- 路线、区域和参数版本对比；
- P50/P90/P95 周期；
- 遥测窗口特征抽取；
- 连续失败和重复故障；
- 基线与实验组差异。

对主要异常场景应提出机制假设，并用控制变量实验复现；只观察相关性不得写成因果结论。

交付物：SQL 文件、EDA 图表、业务分析报告、异常案例和原因验证记录。

验收：核心图表和结论可以通过脚本或 SQL 一键重建；至少一个主要异常完成控制变量验证；报告
同时说明限制和无法支持的结论。

### W7：构建和评估任务失败风险模型

目标：在任务开始前或任务早期识别高风险任务，并与简单业务规则比较。

标签候选：任务最终进入失败、超时、安全停车或需要介入的终态。正式标签必须在建模前冻结。

只允许使用决策时点可获得的特征，例如路线复杂度、参数版本、初始定位协方差、历史近期故障、
以及任务开始后前 3～5 秒的传感器质量。禁止使用最终错误码、最终耗时、任务结束后的恢复次数等
泄漏标签的信息。

至少对比：

- 规则基线；
- Logistic Regression；
- 一种树模型，如 Random Forest、XGBoost 或 LightGBM。

评估至少包括：

- PR-AUC、Precision、Recall、F1 和混淆矩阵；
- 概率校准；
- 不同路线、场景和参数版本下的分组表现；
- 特征重要性或可解释性分析；
- 误报、漏报和典型失败案例；
- 与规则基线的增量价值。

训练/验证/测试集应按实验批次、路线或场景分组拆分，防止同配置的近重复任务跨集合泄漏。

交付物：可复现训练脚本、数据切分清单、基线对比报告、模型卡和错误分析。

验收：独立测试集从训练过程隔离；模型性能优于或明确解释为何未优于规则基线；所有简历模型
数字可由固定版本数据和命令复现。

### W8：把分析结论转化为策略并进行对照实验

目标：证明模型或分析能支持具体运营动作，而不只是产生评分。

候选策略：

- 低风险任务正常执行；
- 中风险任务先重定位再执行；
- 高风险任务拒绝执行或进入模拟人工检查；
- 安全护栏触发时始终覆盖效率策略。

在相同实验矩阵下比较原策略、固定规则策略和模型策略，至少记录：

- 单位仿真时间有效完成任务数；
- 任务完成率；
- P95 任务周期；
- 超时率；
- 恢复/介入率；
- 安全停车率；
- 最小障碍距离；
- 被拦截失败数、误拦截成功数及其业务代价。

交付物：策略定义、对照实验方案、实验结果、统计不确定性和决策建议。

验收：实验组和对照组除策略外保持可比；效率改善不得以明显恶化护栏指标为代价；未取得提升时
如实记录负结果，不选择性报告。

### W9：形成作品集、简历和面试证据包

目标：把技术结果转译成简洁、可信且能经受追问的求职材料。

最终证据包至少包括：

- 一页业务背景、利益相关方和决策问题；
- 指标树和指标字典；
- 数据模型、DDL 和数据血缘；
- 4～8 个核心 SQL；
- ETL 与数据质量报告；
- 数据集规模、分布和版本说明；
- EDA 与失败归因报告；
- 规则、逻辑回归和树模型对比；
- 模型卡、错误分析和局限性；
- 策略对照实验；
- 一条命令可复现主要结果；
- 简历版本、项目介绍版本和面试问答清单。

验收：简历中的每个动词、数字和结论均有仓库证据；能够在不依赖 AI 临场生成答案的情况下，
解释业务口径、取数逻辑、数据质量、SQL、模型选择、泄漏防范、策略权衡及仿真外推限制。
