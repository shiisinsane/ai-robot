# M1测试基线规范

> 版本：M1-W6首版
> 状态：已确认
> 适用范围：M1及后续ROS 2机器人开发
> 技术基线：Ubuntu 22.04、ROS 2 Humble、C++17、Python 3.10

## 1. 目标与边界

W6把W4公共接口和W5运行规则转化为可执行检查，并为后续软件包提供统一测试模板。
当前阶段只建立测试骨架和最小样例，不实现M2机器人本体、正式导航能力或实体运动测试。

W6覆盖单元、节点、Launch、契约和仿真策略测试。rosbag记录、回放、证据外部存储和正式
测试结果元数据模板属于W7。

## 2. 测试分层

| 层级 | 目标 | 当前入口 |
|---|---|---|
| C++单元测试 | 验证与ROS通信分离的普通逻辑 | `ai_robot_cpp_demo/test/test_status_message.cpp` |
| Python单元测试 | 验证普通函数及契约验证器成功、失败分支 | `ai_robot_py_demo/test/`、`tests/unit/` |
| 节点测试 | 验证节点、消息和显式QoS通信 | `tests/node/test_pub_sub_template.py` |
| Launch测试 | 验证节点可被Launch启动并安全停止 | `tests/integration/test_launch_template.py` |
| 契约测试 | 验证名称、类型、QoS、时间、TF和安全规则 | `tests/contract/` |
| 场景测试 | 验证仿真时间策略和后续故障注入场景 | `tests/simulation/` |
| 实体测试 | G1后执行现场设备、运动和安全验证 | `tests/real/`，当前不自动执行 |

每个新对象应先测试不依赖ROS的普通逻辑，再测试节点边界，最后进入子系统和场景测试。
同一断言不应在多个层级无意义重复。

## 3. 机器契约检查

`scripts/check_interface_contract.py`读取`config/common/interface_contract.yaml`，当前检查：

- 接口版本和默认机器人命名空间；
- 15个Topic、2个Service、2个Action的名称和类型唯一性；
- 公共接口使用相对名称且不重复；
- 每个Topic引用有效、有界的QoS配置档；
- 频率和超时值为正数；
- 仿真使用唯一`/clock`，实体不使用仿真时间；
- 安全看门狗使用稳态时钟；
- `map → odom → base_link`存在且每段TF只有一个发布责任；
- 公共接口数量没有未经审查的静默变化。

命令：

```bash
python3 scripts/check_interface_contract.py
```

检查器失败时返回非零退出码并指出具体规则，供本地测试和CI直接判定。

## 4. 统一执行入口

```bash
bash scripts/build.sh
ROS_DOMAIN_ID=61 bash scripts/test.sh
```

`scripts/test.sh`依次执行：

1. `colcon test`运行ROS 2软件包内的C++与Python测试；
2. `colcon test-result --verbose`汇总软件包结果；
3. 机器接口契约检查；
4. 仓库级单元、节点、契约、Launch和仿真策略pytest。

ROS日志统一写入被Git忽略的`log/ros/`，不写入用户主目录。涉及ROS图的并行测试必须分配
不同`ROS_DOMAIN_ID`；CI一次只使用一个明确的隔离域。

## 5. 测试规范

### 5.1 命名

- 文件：`test_<对象>_<行为>.py`或`test_<对象>.cpp`；
- 测试：`test_<前置条件>_<预期结果>()`；
- Fixture：使用能表达输入条件的名称；
- 场景：名称包含`normal`、`timeout`、`disconnect`、`cancel`或具体故障。

### 5.2 输入和预期结果

- 小型确定性输入可以直接写在测试中；
- 跨测试复用或接近真实格式的数据放在`test_data/`；
- 大型图像、rosbag、地图和模型权重不进入普通Git；
- 每项测试必须具有明确断言，不以“进程没有崩溃”作为唯一成功条件；
- 浮点、频率和时延断言必须写明容差及其依据；
- 条件接口未启用时可以跳过，但必须记录跳过原因。

### 5.3 失败与清理

- 失败信息必须指出接口、Frame、QoS策略或场景；
- 测试创建的节点、Executor和子进程必须在`finally`或Launch关闭流程中释放；
- 超时后不得遗留ROS节点或仿真进程；
- 测试不得依赖执行顺序或本机已有节点；
- 预期失败场景必须断言明确的错误，不得把异常吞掉后判为通过。

## 6. 当前最小样例

W6当前验证结果：

- C++ GTest和Python包内pytest：3项通过；
- 仓库级pytest：9项通过；
- C++最小普通逻辑样例通过；
- Python契约验证器的成功及预期失败样例通过；
- ROS 2进程内Publisher/Subscriber通信通过；
- Python节点Launch启动和计划关闭通过；
- 当前接口契约、关键安全超时及仿真时间策略通过。

这些样例只证明测试骨架可以运行，不代表M2～M6机器人能力已经实现或验收。

### 6.1 ROS 2软件包内测试

`colcon test`当前执行两个最小业务断言：

| 软件包 | 测试文件 | 检查内容 |
|---|---|---|
| `ai_robot_cpp_demo` | `test/test_status_message.cpp` | C++普通函数返回预期状态文字，验证GTest及普通逻辑与ROS通信分离的基线 |
| `ai_robot_py_demo` | `test/test_status_publisher.py` | Python普通函数返回预期状态文字，验证包内pytest基线 |

`colcon test-result`显示`3 tests`是ament/CTest对测试结果文件的汇总口径，不表示已经存在
3个机器人业务能力测试。当前明确的业务断言是上表中的一个C++断言和一个Python断言。

### 6.2 仓库级9项测试

| 序号 | 测试 | 文件 | 具体检查 |
|---|---|---|---|
| 1 | 当前契约成功分支 | `tests/unit/test_contract_validator.py` | 正确的`interface_contract.yaml`能够通过验证器 |
| 2 | 错误QoS失败分支 | `tests/unit/test_contract_validator.py` | Topic引用不存在的QoS配置档时，验证器必须拒绝 |
| 3 | 完整机器契约 | `tests/contract/test_interface_contract.py` | 接口数量、名称、类型、QoS、时间和TF规则符合W4/W5 |
| 4 | 安全超时契约 | `tests/contract/test_interface_contract.py` | `cmd_vel`断流`0.2 s`停车，安全状态断流`0.3 s`按停车处理 |
| 5 | 公共名称边界 | `tests/contract/test_interface_contract.py` | 公共接口名称不包含`sim`、`real`、Gazebo版本等实现信息 |
| 6 | ROS节点通信 | `tests/node/test_pub_sub_template.py` | 两个节点使用显式兼容QoS传递并收到预期消息，随后释放节点和Executor |
| 7 | Launch启停 | `tests/integration/test_launch_template.py` | 通过Launch启动Python节点，按计划关闭并正常退出 |
| 8 | 仿真时间策略 | `tests/simulation/test_time_policy_template.py` | 仿真使用`use_sim_time`、全局`/clock`、唯一时钟源及指定QoS |
| 9 | 实体时间隔离 | `tests/simulation/test_time_policy_template.py` | 实体禁用仿真时间，安全看门狗使用稳态时钟 |

这些测试中，第1～5、8、9项主要验证配置和规则；第6项实际建立ROS 2节点通信；第7项
实际经过ROS 2 Launch启动和停止节点。它们不会启动Gazebo、底盘、导航或实体设备。

### 6.3 测试与后续能力的关系

当前W6测试提供的是可复用骨架。后续开发实际模块时：

- 用单元模板测试算法、状态机和参数校验；
- 用节点模板替换示例Topic，验证真实消息、QoS、频率和断流；
- 用Launch模板启动底盘、传感器、定位或导航组合；
- 用契约模板检查仿真与实体接口是否一致；
- 用场景模板加入时间跳变、传感器断开、导航取消和安全停车等故障。

## 7. 后续扩展

W6确认后，后续对象应复用本规范并逐步增加：

- 实际Publisher/Subscriber QoS发现与兼容性测试；

- TF连通性、频率、超时和重复发布者测试；
- Service成功、拒绝和超时测试；
- Action成功、反馈、失败、取消和超时测试；
- 仿真暂停、时间跳变、传感器断流和安全停车场景；
- 仿真与实体配置的公共接口差异检查。
