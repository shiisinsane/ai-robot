# 大厂面试视角：项目漏洞审查与补齐路线

> 审查日期：2026-09-01
> 审查对象：机器人运营数据分析求职支线
> 当前定位：数据分析、分析工程和实验分析项目；尚不是已完成的机器学习项目。
> 执行边界：优先使用现有B1数据补齐作品集，不继续B2采集，不虚构实体或生产收益。

## 1. 总体判断

这个项目已经明显强于“下载CSV、清洗、建模、比较准确率”的课程作业。它能够证明指标设计、数据
治理、SQL分析、实验设计和谨慎解释能力，但目前还存在两个会被专业面试官直接追问的严重漏洞：

1. 正式数据和图表位于Git忽略的`artifacts/`，外部无法验证核心数字；
2. 实验采用15个平衡区组，正式bootstrap却按两个独立组抽样，统计分析没有保留区组结构。

在这两个问题关闭前，不宜把项目包装成“完整、可外部复现的实验决策系统”。

## 3. 关键漏洞的专业说明

### 3.1 外部复现缺口

当前仓库提交了代码、SQL、配置和报告，但正式SQLite/DuckDB数据库、CSV、JSON和SVG都在
`artifacts/`中，并被Git整体忽略。外部只能看到结果文字，无法用公开输入重新生成数字。

应公开的不是完整rosbag，而是一份小型、无敏感信息的分析数据包：

- 45行任务级正式数据；
- `task_id`、`validation_block`、`obstacle_profile`、周期、最大横向偏移及护栏字段；
- 数据字典、来源版本、生成脚本和文件哈希；
- 汇总CSV、统计JSON及展示SVG。

验收标准：在不安装ROS/Gazebo、不访问原始`artifacts/`的环境中，一条命令能够重建公开结果。

### 3.2 区组分析缺口

B1每个`validation_block`包含none、low、medium三个处理，执行顺序在区组内随机。这种设计用于控制
不同运行轮次共享的环境波动。当前统计脚本却分别对两个处理组独立抽样，没有保留同一区组的配对关系。

补齐时不能改写历史，说原分析本来就是区组分析。正确做法是：

1. 保留原预注册独立bootstrap作为主分析历史；
2. 新增明确标记为“事后稳健性分析”的block bootstrap；
3. 每次重采样15个完整区组，同一区组的三档结果一起进入样本；
4. 同时报告区组内差值分布和配对置换检验；
5. 对比原结论的方向、数量级和区间是否一致。

验收标准：代码测试覆盖区组完整性、确定性种子、重采样逻辑和已知小样本；报告不把事后分析冒充
预注册分析。

### 3.3 指标落地缺口

指标树设计本身是项目优势，但当前正式结果只覆盖其中一部分。应建立三态矩阵：

| 指标 | 已定义 | 已实现 | 有正式结果 |
|---|---:|---:|---:|
| 任务完成率 | 是 | 是 | 是 |
| 周期P50/P90/P95 | 是 | 是 | 是 |
| 分阶段失败率 | 是 | 是 | 探索数据可用 |
| 安全停车率/传感器过期率 | 是 | 是 | 是 |
| 单位机器人小时有效任务数 | 是 | 部分 | 否 |
| 准时完成率 | 是 | 受SLA限制 | 否 |
| 真实人工介入率 | 否 | 否 | 否 |

对外表述应使用“设计完整指标体系，并将完成率、周期、场景与安全护栏等核心指标落地”，不写成
“所有指标均已正式计算”。

## 4. 后续实操路线

### S1：冻结作品集口径（已完成）

目的：防止继续扩张任务范围，先把已有成果做成可信成品。

动作：

1. 冻结B1为当前求职展示数据版本；
2. 明确B2风险建模不属于本轮补齐范围；
3. 建立“允许写入简历/仅能说明建设中/禁止使用”三类陈述清单；
4. 修正求职材料中可能过度承诺的指标表述。

产出：`job_search/CLAIM_MATRIX.md`。
验收：已完成；每个数字都有证据，没有PR-AUC、召回率或生产收益占位。

### S2：制作公开任务级数据包

目的：让外部能够验证正式结果，同时不提交大型运行产物。

动作：

1. 从B1事实库导出45行任务级数据；
2. 补入`validation_block`并保留三档处理映射；
3. 删除不必要的本地路径、进程信息和运行环境细节；
4. 生成字段字典、数据版本说明和SHA256；
5. 为导出脚本增加行数、唯一键、区组完整性和空值测试。

计划产出：

```text
job_search/public_data/
├── b1_task_level.csv
├── data_dictionary.md
├── dataset_card.md
└── SHA256SUMS
```

验收：45个唯一任务；15个完整区组；每个区组恰有none、low、medium各一项；无敏感或本地路径。

### S3：补区组稳健性分析（已完成）

目的：修复实验设计与统计方法未完全对齐的问题。

动作：

1. 实现区组内处理差值；
2. 对完整区组执行10,000次block bootstrap；
3. 增加配对置换检验或随机化检验；
4. 将结果与原独立bootstrap并列；
5. 清楚标记为事后稳健性分析。

计划产出：

```text
job_search/analysis/
├── analyze_public_b1.py
├── block_robustness.json
├── block_effects.csv
└── README.md
```

验收：已完成；相同种子结果确定，测试覆盖区组完整性和精确随机化，报告确认结论方向未改变。

### S4：生成招聘者可读图表

目的：让面试官在一分钟内看到数据、实验和结果。

动作：

1. 制作数据链路图；
2. 制作45项任务级周期散点图，展示区组和三档处理；
3. 制作原分析与区组稳健性分析的效应区间图；
4. 制作旧设计混杂与B1纠正设计的对比图。

计划产出：`job_search/figures/`下3～4张SVG或PNG。
验收：标题、单位、样本量、95%区间和“仿真”边界完整；图可以独立阅读。

### S5：建立一键外部复现

目的：让招聘者不安装ROS也能运行分析。

动作：

1. 新建最小分析依赖文件，包含Python、DuckDB、PyYAML和pytest等实际依赖；
2. 提供单一复现命令；
3. 从公开CSV重建统计表与图；
4. 增加公开数据与结果快照测试；
5. 在干净环境中执行验证。

计划产出：

```text
job_search/requirements.txt
job_search/reproduce.sh
job_search/tests/
```

验收：不读取`artifacts/`，不依赖ROS；命令退出码为0；结果与证据索引数字一致。

### S6：补业务决策情景分析

目的：回答如何区分复杂但正常的慢任务与真正异常，并把耗时差异转化为任务预算、异常升级、容量和
路线选择依据。

当前状态：`../technical/DECISION_ANALYSIS_CONTRACT.md`已冻结；分析代码、结果和决策备忘待完成。

动作：

1. 基于已有任务周期设置多个候选任务预算，不伪造真实SLA；
2. 比较统一预算与按任务难度分档预算下，成功任务被标记为超时的数量；
3. 计算不同复杂任务占比下的理论任务容量和调度缓冲；
4. 计算备选路线额外耗时与继续绕行代价的盈亏平衡范围；
5. 报告潜在误报、额外等待时间和必须监控的安全护栏；
6. 将结论写成决策备忘，而不是生产收益声明。

计划产出：`job_search/DECISION_MEMO.md`和一张阈值敏感性图。
验收：明确是情景分析；展示假设敏感性；不使用“节省真实成本”等措辞。

### S7：重构招聘者首页

目的：让README从内部实施计划变成作品集首页。

动作：

1. 将README正文压缩到约100～150行；
2. 依次展示一句话价值、核心数字、三张图、个人职责、复现命令和限制；
3. 将W0～W7过程文档放到技术索引，不在首页展开；
4. 检查所有链接在仓库页面可点击。

验收：不了解ROS的面试官在两分钟内能回答项目问题、个人贡献、结果、价值和限制。

## 5. 推荐执行顺序与停止点

```text
S1口径冻结
  → S2公开数据包
  → S3区组稳健性分析
  → S4核心图表
  → S5一键复现
  → S6决策情景分析
  → S7首页重构
```

S1～S5是必须完成项；完成后项目具备可信的外部作品集形态。S6～S7用于提高招聘转化。当前不建议
恢复B2采集，也不建议为了补机器学习标签而无限扩展本项目。若目标岗位强制要求建模证据，应另建一个
具备自然标签、独立测试集和明确业务损失函数的项目。

## 6. 完成后的项目定位

补齐后最准确的定位是：

> 独立完成机器人仿真运营指标体系、数据管道、SQL诊断和预注册实验，并通过公开数据、区组稳健性
> 分析及一键复现证明结论可信的实验分析项目。

它可以有力证明数据分析、分析工程和实验设计能力；不用于声称已经具备生产级失败预测模型或实体
机器人业务收益。
