- 新增`ekf_m4.yaml`，采用`robot_localization 3.5.4`的`ekf_node`；
- 输入`/robot/internal/base_odom`中的平面位置、航向、纵向速度和角速度；

- EKF在差速控制器激活后启动，避免输入尚未就绪时提前接管公共里程计和TF。

## 4. 用户GUI人工验证

### 4.1 准备与启动

本验证仅用于仿真，不连接实体设备。准备两个终端，均在仓库根目录执行命令。

终端1启动Gazebo和RViz：

```bash
cd /home/yangyiyao/ai_robot
source /opt/ros/humble/setup.bash
source install/setup.bash
ros2 launch ai_robot_sim integrated_bringup.launch.py gui:=true rviz:=true
```

等待Gazebo中出现完整机器人和前方红色障碍物，并等待RViz窗口启动。启动期间应确认终端没有
节点提前退出、控制器加载失败或EKF进程退出信息。

终端2加载同一环境，供后续发送仿真速度命令：

```bash
cd /home/yangyiyao/ai_robot
source /opt/ros/humble/setup.bash
source install/setup.bash
```

### 4.2 配置RViz

1. 在左侧`Displays`中展开`Global Options`，将`Fixed Frame`设为`odom`。当前阶段不发布
   `map → odom`，不得使用`map`作为固定坐标系；
2. 点击左下角`Add`，依次添加`RobotModel`、`TF`、`Odometry`和`LaserScan`；
3. 展开`Odometry`，点击`Topic`右侧的下拉框，选择`/robot/odom`；保持
   `Reliability Policy=Reliable`；
4. 展开`LaserScan`，将`Topic`设为`/robot/scan`，并将`Reliability Policy`设为
   `Best Effort`；可将`Style`设为`Points`、`Size (m)`设为`0.03`、`Decay Time`设为
   `1`，便于观察；
5. 展开`TF`，确认树中存在`odom → base_link`，并能从`base_link`继续看到
   `laser_link`、`camera_link`、`camera_color_optical_frame`、`imu_link`和车轮Link；
6. 确认`RobotModel`正常显示。Odometry和LaserScan刚加入且未选Topic时显示红色属于未配置
   状态；完成上述配置后应恢复正常。如果TF仍为黄色，应展开其`Status`读取具体警告，不把
   未关闭的警告直接判定为通过。

### 4.3 静止观察

机器人保持静止约5秒，检查：

- Gazebo中的机器人没有自行移动或旋转；
- RViz中的RobotModel稳定，没有明显跳变；
- `odom → base_link`持续存在；
- `/robot/odom`显示正常，LaserScan能看到红色障碍物等环境点；
- Odometry、LaserScan和RobotModel没有持续红色错误状态。

### 4.4 直行验证

在终端2发送低速直行命令：

```bash
ros2 topic pub -r 10 /robot/safety_cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.2}, angular: {z: 0.0}}"
```

只运行约2～3秒，随后按`Ctrl+C`停止命令发布。观察并确认：

- Gazebo中机器人沿自身X轴正方向前进；
- RViz中RobotModel与Gazebo运动方向一致；
- Odometry连续变化，没有突然跳跃、倒退或出现非有限值；
- TF中的`base_link`相对`odom`连续移动；
- 直行期间航向基本稳定。

不要持续驶向红色障碍物。该障碍物距离初始位置较近，直行过久会发生真实物理碰撞，影响后续
原地转向观察。

### 4.5 原地左转验证

确认机器人与红色障碍物有足够间距后，在终端2执行：

```bash
ros2 topic pub -r 10 /robot/safety_cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.0}, angular: {z: 0.6}}"
```

观察约2～3秒后按`Ctrl+C`。检查：

- Gazebo中机器人逆时针原地左转；
- RViz中的RobotModel和`base_link`同步逆时针旋转；
- `/robot/odom`航向连续增加，没有明显跳变；
- 激光扫描随机器人朝向同步旋转，仍可通过TF解释到`odom`坐标系。

### 4.6 碰撞恢复

如果机器人已接触红色障碍物并出现难以转向，先低速后退：

```bash
ros2 topic pub -r 10 /robot/safety_cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: -0.2}, angular: {z: 0.0}}"
```

后退约0.5～1米后按`Ctrl+C`，确认脱离障碍物，再执行原地转向。如果仍被卡住，关闭并重新启动
统一Bringup，使机器人恢复初始位姿，不在碰撞接触状态下判断EKF或TF是否异常。

### 4.7 停车与关闭

`Ctrl+C`只停止速度命令发布程序；控制器因0.2秒命令超时通常会自动停车。为明确结束状态，
可在终端2额外发送一次零速度：

```bash
ros2 topic pub --once /robot/safety_cmd_vel geometry_msgs/msg/Twist "{}"
```

确认Gazebo中的机器人停止后，到终端1按`Ctrl+C`关闭统一Bringup。检查适配器、EKF、状态发布器
和控制器完成退出，没有残留的运动命令发布进程。

### 4.8 人工验收结论

用户于2026年8月6日按上述流程完成验证。RobotModel显示正常；完成Topic与QoS配置后可观察
状态估计和雷达数据；机器人直行、后退和左转方向符合预期，Gazebo、融合里程计及TF表现一致，
W4 GUI人工验证通过。

本次验证同时形成以下操作经验：

- 初次加入Odometry和LaserScan时显示红色通常是尚未配置Topic；LaserScan还必须将订阅可靠性
  设置为Best Effort，否则与公共雷达QoS不兼容；
- Fixed Frame应使用`odom`，当前阶段没有`map → odom`；
- 统一世界中的红色物体是雷达测试障碍物，连续直行会发生真实物理碰撞并影响原地转向；后续
  人工测试应将直行限制在约2～3秒，先停车并确认与障碍物有足够间距，再测试转向；
- 若已接触障碍物，应先以低速后退约0.5～1米，停车后再原地转向；必要时重启仿真恢复初始位姿；
- `Ctrl+C`只停止命令发布程序，当前控制器会因0.2秒命令超时自动停车；额外发送一次零速度是
  明确、安全的收尾动作，但在已确认超时停车后不是本阶段通过的强制条件。

## 5. 已知边界

- 当前EKF仅提供`odom`局部状态估计，不发布`map → odom`，不包含SLAM或全局定位；
- 左转融合角度受IMU与编码器协方差权重影响，与原始里程计存在合理差异；
- 本阶段未进行轮胎打滑、传感器断流或故障停车验证，这些留待W7；
- 雷达运动中TF解释、障碍物语义和断流测试留待W5。
